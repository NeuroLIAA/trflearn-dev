    Search¶

    Hyperparameter search spaces: the per-band regularization grids of a banded ridge, factored into a band ratio and a global scale so one eigendecomposition serves a whole scale sweep. Why that split is what makes a banded search affordable is below; Solvers covers the solve it feeds.

    search ¶

    search.py — Which regularization strengths to try.

    models owns how a model is fitted and solvers owns the numeric solve; this module owns the third question: which hyperparameters get tried, and in what order. It knows nothing about designs, folds or targets -- everything here is arithmetic on small arrays of regularization strengths.

    A BandSearch is that list of strengths, plus the band names its columns refer to. Nothing more: a search says what to try, and solvers decides how to solve it. An ordinary regularization grid is the case where every vector is uniform, and is built as exactly that rather than as a special shape.

    Why a λ vector gets split in two

    A banded ridge gives each group of features its own regularization strength, so the hyperparameter stops being a number and becomes an (n_bands,) vector. Searching over vectors is where the cost explodes: five values over four bands is 625 λ values, and the naive way to run them is 625 separate solves per fold.

    Most of that work is avoidable, and seeing why is the point of this module. Write any positive λ vector as ::

    λ = scale * ratio        ratio normalized to geometric mean 1

    The ratio says which band is penalized harder than which -- the direction of the vector. The scale says how strongly the model is regularized overall -- its size. Normalizing the ratio makes the split unique: scale = geomean(λ).

    The split earns its place because the two halves cost completely different things to change. Moving the scale is nearly free: with the ratio held fixed, every scale in a sweep comes out of one eigendecomposition of the design, reused. Moving the ratio is not: a new direction needs a new factorization. So what a search costs is governed by how many ratios it holds, not by how many λ values -- and two searches of the same size can differ by an order of magnitude.

    That is what random_bands exploits and what band_grid cannot: a random search draws a handful of ratios and sweeps the whole scale grid at each, where a Cartesian product spends most of its ratios on corners carrying a single scale. band_grid has the arithmetic.

    The factorization is derived, not stored. BandSearch keeps the λ vectors and computes the split on demand, for the two questions that need it: what single number puts a banded fit on the x axis of the validation figure, and which λ values belong to the same curve. solvers recovers its own grouping from the per-column weights it receives, and never reads this one.

    Vocabulary

    band A named group of design blocks sharing one λ, from the model's feature_groups. With no feature_groups every feature is its own band. ratio The direction of a λ vector: (n_bands,), positive, geometric mean 1. The banded-ridge literature writes it gamma. scale The size of a λ vector: one positive number, the geometric mean of its entries. It is what random_bands(scales=...) sweeps and what the search reports as best_scale; for an ordinary ridge it is λ itself. regularization One regularization strength to try, λ -- here always an (n_bands,) vector. n_values counts them; an ordinary scalar λ is the uniform case.

    Axis names follow the package glossary in docs/concepts/notation.md.

    summary_scale ¶

    summary_scale(regularization: Strengths) -> float

    One number standing for a per-band λ vector: its geometric mean.

    Parameters:

    Name Type Description Default
    regularization sequence of float or np.ndarray

    An (n_bands,) λ vector. Zeros are tolerated here, unlike in normalize_ratio.

    		 required

    Returns:

    Type Description
    float

    The scale. 0.0 for an empty input; the arithmetic mean when any band is unpenalized.
    Notes

    The same lambda the search is parametrized by, which is what makes it the right summary rather than merely a defensible one -- a scalar fit and a banded fit are then reported on the same axis.

    Arithmetic would be wrong here, and not subtly. Regularization strengths live on a log scale and routinely span orders of magnitude, so the mean of {10, 10000} is 5005 -- a number nearer the larger band than to anything the model does -- where the geometric mean is 316, the scale a single-λ fit of comparable shrinkage would have used.

    It falls back to the arithmetic mean if any band is unpenalized, where the geometric mean collapses to zero and stops distinguishing anything.

    normalize_ratio ¶

    normalize_ratio(
    regularization: Strengths,
) -> tuple[float, ndarray]

    Split a positive λ vector into a scale and a ratio.

    Parameters:

    Name Type Description Default
    regularization sequence of float or np.ndarray

    A strictly positive (n_bands,) λ vector.

    		 required

    Returns:

    Name Type Description
    scale float

    The global multiplier, geomean(λ).
    ratio ndarray

    (n_bands,), geometric mean 1.

    Raises:

    Type Description
    ValueError

    If regularization is empty, non-finite, or not strictly positive.
    Notes

    The inverse of λ = scale * ratio, and unique: taking the geometric mean of both sides gives geomean(λ) = scale * 1. The scale comes from summary_scale, so the two functions cannot disagree about what a vector's scale is.

    from_values ¶

    from_values(
    values: ndarray | Sequence, band_order: BandNames
) -> BandSearch

    Build a search from explicit λ vectors.

    Parameters:

    Name Type Description Default
    values np.ndarray or nested sequence

    (n_values, n_bands), one row per λ vector, strictly positive.

    		 required
    band_order sequence of str

    The model's band order; names the columns.

    		 required

    Returns:

    Type Description
    BandSearch

    The search, with the rows normalized as described below.

    Raises:

    Type Description
    ValueError

    If values is not 2-D, its column count disagrees with band_order, or a row is not strictly positive.
    Notes

    Rows are normalized before being stored: grouped by ratio in first-appearance order, and sorted ascending by scale within each group, with duplicates dropped. The λ numbering is therefore a function of the set of vectors handed in, not of the order they happened to be written in -- so two callers who list the same space differently get the same figure and the same best_index.

    scalar_grid ¶

    scalar_grid(
    values: Strengths, band_order: BandNames

    The ordinary (unbanded) regularization grid, as the one-ratio search it is.

    Parameters:

    Name Type Description Default

    The grid to sweep. Zeros are allowed -- an unregularized fit.

    		 required
    band_order sequence of str

    The model's band order; names the columns.

    		 required

    Returns:

    Type Description
    BandSearch

    (len(values), n_bands), every row uniform.

    Raises:

    Type Description
    ValueError

    If values is empty, non-finite, or negative.
    Notes

    Every band gets the same λ, so the ratio is all ones and the grid is the lambda sweep. Keeping this in the same type as a banded space is what lets models.TorchTRF.gridsearchCV run one loop instead of two.

    band_grid ¶

    band_grid(
    grids: dict[str, Strengths] | Strengths,
    band_order: BandNames,
    *,
    max_values: int = MAX_VALUES
) -> BandSearch

    Cartesian product of a per-band grid.

    Parameters:

    Name Type Description Default
    grids dict of str to sequence, or sequence of float

    {band: values}. A band left out of the dict reuses the grid of the single band that was given, if exactly one was; otherwise its absence is an error, since silently regularizing a band at one fixed value while sweeping the others is a search a caller would not notice they had asked for. A bare sequence is applied to every band.

    		 required
    band_order sequence of str

    The model's band order; fixes the column order of the result.

    		 required
    max_values int

    Refuse products larger than this. n_bands bands at n_values each is n_values ** n_bands solves per fold, which passes "large" quickly: 10 values over 4 bands is 10,000.

    		 MAX_VALUES

    Returns:

    Type Description
    BandSearch

    The product, in the ratio order from_values imposes.

    Raises:

    Type Description
    KeyError

    If grids names a band the model does not have, or leaves one without a grid when more than one was given.
    ValueError

    If the product would exceed max_values, or a grid is empty, non-finite or not strictly positive.
    Notes

    The product is generated directly, because {band: grid} is how a caller thinks about it, and from_values then puts it in ratio order. That ordering exposes the structure a product hides: an n_values by n_values log-spaced grid over two bands contains only 2 * n_values - 1 distinct ratios, its diagonals.

    Be aware that a product is nonetheless the worst shape for the eigendecomposition path in solvers, which needs a run of scales at one ratio to pay for itself: the diagonals of a product are long but its corners hold a single scale each, so most groups fall back to an ordinary solve. random_bands sweeps the whole lambda grid at every ratio and is the shape that path was built for. Prefer it when the search is large enough for the difference to matter.

    random_bands ¶

    random_bands(
    band_order: BandNames,
    *,
    n_ratios: int = 20,
    scales: Strengths | None = None,
    concentration: float = 1.0,
    random_state: int | None = 42
) -> BandSearch

    Random search: ratios drawn uniformly on the simplex, times a lambda grid.

    Draws n_ratios Dirichlet samples and sweeps the full scales grid at each, for n_ratios * len(scales) λ values whose cost does not grow with the number of bands -- the reason to prefer this over band_grid past two or three of them. It is the strategy of Nunez-Elizalde et al. (2019), on the Bergstra & Bengio argument that for a fixed budget random draws cover the directions that matter better than a grid does as the dimension rises.

    Parameters:

    Name Type Description Default
    band_order sequence of str

    The model's bands; sets the dimension of the simplex.

    		 required
    n_ratios int

    How many ratio vectors to draw.

    		 20
    scales sequence of float or np.ndarray

    Global scales swept at every ratio. Defaults to np.logspace(-2, 6, 20), the span an unnormalized ridge on standardized features usually needs.

    		 None
    concentration float

    Dirichlet concentration. 1.0 is uniform over the simplex; below 1 favours lopsided ratios (one band carrying most of the penalty), above 1 favours near-equal ones.

    		 1.0
    random_state int or None

    Seed. Fixed by default for the same reason models.TorchTRF._bootstrap_metric fixes its own: two runs of the same model should select the same λ and report the same metric, and a search whose result moves between runs is not one a paper can cite.

    		 42

    Returns:

    Type Description
    BandSearch

    (n_ratios * len(scales), n_bands), one ratio's whole sweep after another.

    Raises:

    Type Description
    ValueError

    If n_ratios is below 1, or scales is empty, non-finite or not strictly positive.
    Notes

    A Dirichlet sample sums to 1, so it is rescaled to geometric mean 1 to match the module's convention. That is a relabelling of the same direction: what the draw fixes is the proportion between bands, and the overall size is what scales sweeps.

    Normalize whatever gridsearchCV was handed into a BandSearch.

    Parameters:

    Name Type Description Default
    regularization_grid (BandSearch, dict, sequence, ndarray or None)

    Accepted, and how each is read:

    None DEFAULT_REGULARIZATION_GRID, as an ordinary grid. BandSearch returned unchanged (the output of band_grid / random_bands). 1-D sequence an ordinary regularization grid -- always, never a per-band vector.
